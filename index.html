설계 의사결정

세션 대신 JWT(Access + Refresh)를 선택
프론트엔드와 백엔드를 독립적으로 배포하고 API 서버의 세션 상태 의존도를 낮추기 위해 JWT 기반 인증을 선택했습니다. Access 토큰은 짧게 유지하고, Refresh 토큰은 원문이 아닌 해시(token_hash)로 별도 테이블에 저장해 재발급과 강제 로그아웃을 서버에서 통제할 수 있도록 했습니다.
메뉴 숨김이 아니라 서버 API 인가 검증을 기본으로
프론트에서 메뉴만 숨기면 API를 직접 호출해 우회할 수 있습니다. 프론트에서 1차로 접근을 막고, 백엔드 SecurityConfig에서 역할 기반 접근 제어를 다시 구성해 인증 실패(401)는 JwtAuthenticationEntryPoint, 인가 실패(403)는 JwtAccessDeniedHandler로 분리했습니다.
임시 비밀번호 대신 이메일 링크 기반 초기 설정
임시 비밀번호를 구두 · 메신저로 전달하는 방식은 유출 위험이 있어, 계정 생성 시 passwordInitialized = false로 시작해 이메일 링크로만 최초 비밀번호를 설정하게 했고 그 전에는 로그인 자체를 차단했습니다.
문제
무효한 JWT 토큰이 필터 체인에서 즉시 차단되지 않고 다음 단계로 전달됨
해결
필터 체인 진행을 중단하고 즉시 401 응답을 반환하도록 필터 로직을 수정
문제
견적 상태가 바뀔 때마다 사용자 통계(견적 수·승인/반려/발송 건수·총액·평균 할인율)를 갱신해야 하는데, 전체 견적을 애플리케이션으로 가져와 반복 계산하면 데이터가 늘어날수록 연산 부담이 커지고 상태 변경 순서에 따라 결과가 달라질 위험이 있음
해결
애플리케이션 순회 계산 대신 QueryDSL 집계 쿼리(CASE-WHEN + SUM)로 견적 테이블 전체를 재계산하도록 변경해, 상태 변경 순서와 관계없는 멱등 구조를 구성 (애플리케이션 계산 vs DB 집계 비교에 해당하는 실제 설계 근거). 동시 수정이 가능한 UserStats 엔티티에는 @Version 기반 낙관적 락을 별도로 적용
인증
401(인증 실패)과 403(인가 실패)의 처리 책임을 분리하고, 권한 검증을 서버(SecurityConfig) 기준으로 일원화했습니다.
데이터
사용자 통계를 애플리케이션 순회 대신 DB 집계 쿼리로 전체 재계산하는 멱등 구조로 설계해, 상태 변경 순서와 무관하게 항상 같은 결과를 보장합니다. 담당 도메인에는 132개 테스트 케이스를 작성했습니다.
배포
GitHub Actions 기반으로 빌드 → GHCR 푸시 → SSH 배포 → 컨테이너 재기동까지 7단계를 git push 1회로 자동 실행하도록 구축했습니다. 이미지를 커밋 SHA로 태깅해 보관하므로, 문제 발생 시 이전 SHA 이미지로 재배포할 수 있는 기반을 마련했습니다.

무효 토큰 요청 시 필터 체인 처리 흐름 — 버그(위) vs 수정 후(아래)
backend/.../global/security/JwtAuthenticationFilter.java
if (!jwtTokenProvider.validateToken(token)) {
    // 무효 토큰 → 필터 체인 진행을 즉시 중단하고 401 반환
    SecurityContextHolder.clearContext();
    jwtAuthenticationEntryPoint.commence(
        request, response,
        new BadCredentialsException("유효하지 않은 토큰입니다.")
    );
    return;   // ← 수정 전엔 이 return이 없어 체인이 계속 진행됐음
}
// 이후: SecurityContext에 Authentication 저장 후 필터 체인 통과

// 취소: ACTIVE → CANCEL_RESERVED (endedAt은 그대로, 만료 전까지 혜택 유지)
@Transactional
public SubscriptionStatusResponse cancel() {
    List<Subscription> activeSubscriptions = subscriptionRepository.findAllActiveByMemberId(memberId);
    activeSubscriptions.forEach(Subscription::cancel);  // 상태만 변경
    return SubscriptionStatusResponse.from(activeSubscriptions.get(0));
}

// [스케줄러, 매 정각] 만료 대상 일괄 처리
for (Subscription s : expired) {
    if (s.getStatus() == SubscriptionStatus.CANCEL_RESERVED) {
        s.expire();                              // → EXPIRED
        member.changeRole(MemberRole.USER);      // 역할 복원
    } else if (s.getStatus() == SubscriptionStatus.ACTIVE) {
        s.expire();                              // 기존 구독 종료
        subscriptionRepository.save(Subscription.createMock(member)); // 신규 구독 생성(자동 갱신)
    }
}

지역 동기화를 순차 호출 → 청크 단위 병렬 호출로 개선
페이지를 하나씩 순차 호출해 전체 동기화에 최대 1분 가까이 걸렸습니다. 첫 응답에서 전체 데이터 수를 먼저 확인해 필요한 페이지 수를 계산하고, 남은 페이지를 청크로 나눠 병렬 호출하도록 바꿔 전체 동기화 시간을 최대 약 1분에서 10초 미만으로 단축했습니다.
지역 매핑 조회에 메모리 캐시 적용
외부 데이터 건마다 내부 지역을 매번 DB에서 조회하면 데이터 건수만큼 조회가 반복됩니다. 전체 지역 데이터를 한 번만 조회해 메모리 캐시로 올려두고, 이후에는 캐시에서 바로 찾도록 구현해 반복 조회 비용을 줄였습니다.

해결

DESC) SQL 윈도우 함수로 DB에서 한 번에 집계·정렬하도록 설계해, 사용자 수가 늘어나도 애플리케이션 서버가 별도 순회 연산을 하지 않는 구조를 확보했습니다. 담당 영역 기준 API 12개(랭킹 2, 인증서 6, 지역 4), 테이블 3개(region, volunteer_region_mapping, certificate_submission)를 구현했습니다.

핵심 문제 딥다이브

알고리즘 설계

출발지 전원의 이동시간 편차를 최소화하는 지점을 찾을 때, 극단적으로 먼 출발지 하나 때문에 전체 추천이 나빠질 수 있어 출발지를 하나씩 제외한 N-1 조합까지 비교해 더 균형 잡힌 지점을 선택하도록 설계했습니다.

N개 전체 계산과 N-1 부분집합 계산을 비교해 최종 지점을 채택하는 흐름
backend/.../service/StationMidpointService.java
// ① 전체 N개로 계산
StationMidpointResponse fullResp = computeMidpoint(session, sourceNames, idToName, graph);

// ② 출발지를 하나씩 빼고(N-1) 재계산해 더 나은 조합이 있는지 탐색
for (int i = 0; i < N; i++) {
    List<String> subset = new ArrayList<>(sourceNames);
    subset.remove(i);
    StationMidpointResponse r = computeMidpoint(session, subset, idToName, graph);
    if (r != null && (bestSubset == null
            || r.getTimeDifference() < bestSubset.getTimeDifference())) {
        bestSubset = r;
        removedIdx = i;
    }
}

// ③ 제외된 출발지의 실제 소요시간으로 보정한 뒤에도
//    편차·최댓값이 fullResp보다 개선될 때만 N-1 결과를 채택
if (augDiff < fullResp.getTimeDifference() && augMax < fullResp.getMaxTime()) {
    return new StationMidpointResponse(sourceNames, bestSubset.getBalancedMidpoint(), augTimes, augDiff);
}
